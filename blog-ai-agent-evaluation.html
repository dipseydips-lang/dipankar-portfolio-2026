How to Evaluate AI Agents: A Practical Framework for Reliability, Safety and Real-World Performance

An AI agent can complete a complicated task in a demonstration and still be a poor production system. The difference is not necessarily the model. It is the environment around the model: tools, permissions, retrieval, external services, memory, state changes, failure handling and the rules that determine when the system should stop.

That makes agent evaluation fundamentally different from checking whether a language model generated a good answer.

A conventional model evaluation can often be reduced to a simple relationship: input goes in, output comes out, and the output is compared with an expected result. An agent introduces a chain of decisions between those two points. It may interpret the request, retrieve information, select a tool, construct arguments, inspect the result, revise its plan, call another tool and finally produce an answer or take an action.

Every one of those steps creates another opportunity for failure.

A useful evaluation framework therefore has to answer more than one question. Did the agent complete the task? Did it use the right information? Did it select appropriate tools? Were the tool arguments valid? Did it respect permissions? Did it recover sensibly when something failed? Did it create an unintended side effect? Did it know when human intervention was required?

These questions matter because an agent can arrive at the correct answer through an unsafe path, or arrive at a plausible answer after making several serious mistakes.

Why a successful demo proves very little

Agent demonstrations usually operate under unusually favorable conditions. The task is clearly defined. The available tools work. The data is clean. The user request is cooperative. There are no unexpected permission errors, ambiguous records or conflicting sources. The agent may also be given a narrow environment designed around the exact workflow being demonstrated.

Production environments do not behave that way.

A customer support agent may encounter an account with incomplete information. A procurement agent may discover that a supplier record has changed. A finance workflow may contain two transactions that appear similar but require different treatment. An internal research agent may retrieve an outdated document. A security agent may encounter hostile instructions embedded inside a document it was asked to summarize.

The final response can still look convincing.

That is the dangerous part.

Agent evaluation must therefore examine the execution path as well as the outcome. Current evaluation work increasingly treats the complete trajectory as the object being measured, including tool calls, intermediate decisions, safety behavior and recovery. The agent is the system, not the model

It is tempting to evaluate an agent by asking which underlying model it uses. That can be useful, but it does not answer the production question.

Consider an enterprise agent with seven components:

  • a foundation model that interprets instructions and generates decisions
  • a retrieval layer that supplies documents or structured information
  • a tool layer containing APIs and business actions
  • an orchestration layer that manages the workflow
  • memory or state that persists information between steps
  • an identity and authorization layer that controls access
  • an application layer that determines what happens after an action is requested

If the agent produces a wrong result, any one of these layers could be responsible.

The model might misunderstand the request. Retrieval might return stale information. The tool might receive an invalid parameter. Authorization might be too broad. The orchestration logic might allow an unnecessary retry loop. The external service might return an error that the agent does not understand.

Calling the entire failure a "hallucination" does not help the engineering team fix it.

A useful evaluation program assigns observable checks to each layer. That creates a failure map instead of a single accuracy number.

A practical evaluation model

A production-oriented framework can be organized around six dimensions:

  1. Outcome: Did the agent accomplish the intended task?
  2. Trajectory: Did it take a reasonable and policy-compliant path?
  3. Tool use: Did it choose the correct tools and provide valid arguments?
  4. Safety: Did it stay inside its authorization and security boundaries?
  5. Recovery: Did it handle uncertainty, failure and escalation appropriately?
  6. Operations: Did it meet acceptable latency, cost and reliability requirements?

These dimensions should not necessarily be collapsed into one score. A weighted score can hide serious weaknesses. An agent with excellent task completion but poor authorization behavior should not receive a passing grade because its average score looks strong.

For high-impact workflows, some criteria should be treated as gates. For example, an agent might be required to achieve a minimum task-success rate while also recording zero unauthorized state-changing actions. A failure in the second category should remain visible even if the overall score is high.

1. Start with the task, not the model

The first step in evaluation is to define what success means for the actual workflow.

"Answer customer questions accurately" is too vague for a serious evaluation set. A better task definition might specify that the agent must identify the customer's account, retrieve the latest approved policy, determine whether the request is eligible, provide the correct response and create a support ticket only when escalation criteria are met.

That definition creates several testable conditions.

The agent must identify the correct record. It must retrieve the correct policy. It must interpret eligibility correctly. It must provide an answer grounded in the approved source. It must not create a ticket unnecessarily. It must create one when the escalation rule applies.

Now the workflow can be tested at several levels.

End-state correctness asks whether the requested business outcome was achieved.

Action correctness asks whether the state changes were appropriate.

Evidence correctness asks whether the result was based on valid information.

Policy correctness asks whether the workflow stayed within its defined rules.

This approach is more useful than simply asking whether the final response "sounds right."

2. Evaluate the trajectory, not just the destination

Two agents can produce the same final answer while following very different paths.

Suppose an agent is asked to identify the status of an order. The correct path may involve retrieving the order from the commerce platform and checking the latest fulfillment event. An inefficient agent might search a general knowledge base, call an analytics API, retry the wrong endpoint and eventually retrieve the correct record.

If only the final answer is evaluated, both agents pass.

Operationally, they are not equivalent.

The second agent consumed more resources, introduced unnecessary failure points and may have behaved dangerously under slightly different conditions. Trajectory evaluation makes those differences visible.

Useful trajectory signals include:

  • tool selection and ordering
  • number of tool calls
  • unnecessary retries
  • repeated retrieval of identical information
  • use of stale or irrelevant context
  • failure to stop after a definitive result
  • attempts to access information outside the task scope
  • actions taken after a permission or validation failure

The goal is not to force every agent to follow one rigid sequence. Different valid paths can exist. The evaluation should distinguish between acceptable variation and behavior that creates unnecessary risk.

3. Tool use deserves its own scorecard

Tool use is one of the most important differences between an ordinary language model and an agent.

A tool call can fail in several distinct ways.

The agent can select the wrong tool. It can select the correct tool but use the wrong parameter. It can pass a syntactically valid parameter that refers to the wrong record. It can make the same call repeatedly. It can call a tool when no call was necessary. It can ignore a tool result. Or it can interpret a successful API response as proof that the requested business action actually succeeded.

These should not be treated as one category.

Failure typeWhat to test
Tool selectionWas the appropriate capability selected?
Schema validityWere required fields and data types correct?
Argument correctnessDid the parameters refer to the intended entity and operation?
Permission complianceWas the requested action authorized?
Result interpretationDid the agent correctly understand the tool response?
Side-effect correctnessDid the external state change match the intended action?
TerminationDid the agent stop when the task was complete?

This separation turns an abstract agent failure into an engineering diagnosis.

4. A successful API response is not necessarily a successful task

This distinction is easy to overlook.

An API may return a valid HTTP response even though the business operation did not produce the intended result. An update request may be accepted but applied to the wrong record. A search endpoint may return an empty result because the parameters were incorrect. A ticketing system may create a duplicate because the agent retried after a timeout without confirming whether the first request succeeded.

Evaluation should therefore include state verification wherever possible.

For a state-changing action, the test should ask not only whether the tool call returned successfully, but whether the resulting state is correct. This is particularly important for financial transactions, account changes, procurement actions, customer records and other workflows where a duplicate or unauthorized action can create real consequences.

Idempotency, transaction status and post-action verification are therefore evaluation concerns, not merely backend implementation details.

5. Safety is an evaluation category, not a policy document

Security controls are meaningful only when they can be tested.

An agent that has access to business tools needs explicit boundaries around what it may read, modify or trigger. Least privilege should be enforced by the surrounding system rather than left entirely to the model's interpretation of an instruction.

This becomes especially important when the agent processes untrusted information.

A document, webpage, email or database record can contain text that looks like an instruction. If the agent treats every piece of retrieved text as an authoritative command, the information source can influence behavior beyond its intended role. NIST has specifically studied agent hijacking and indirect prompt injection, where malicious instructions embedded in data can cause an agent to take unintended actions. citeturn0search16

Evaluation should therefore include adversarial cases.

Examples include:

  • a retrieved document containing instructions unrelated to the user's request
  • a webpage asking the agent to reveal hidden information
  • a tool response containing unexpected instructions
  • a user attempting to bypass an authorization boundary
  • conflicting instructions from different sources
  • a request that requires human approval before a state-changing action

The important measurement is not simply whether the agent refuses. It is whether the agent recognizes the boundary, avoids unsafe action and provides an appropriate next step.

6. The agent needs to know when it does not know

Reliable automation requires calibrated uncertainty.

An agent should not treat every task as something it must complete autonomously. Some requests are ambiguous. Some records conflict. Some tools return incomplete information. Some actions require approval.

A mature workflow defines escalation conditions.

For example, an agent might be permitted to answer routine questions automatically but required to escalate when identity cannot be verified, when two authoritative records conflict, when a transaction exceeds a threshold or when the requested action changes a sensitive account attribute.

Evaluation can then measure escalation quality.

  • Did the agent escalate when it should have?
  • Did it avoid unnecessary escalation?
  • Did it provide the human reviewer with the relevant evidence?
  • Did it preserve the state needed to continue the task?
  • Did it clearly explain why intervention was required?

Human review is not necessarily evidence of an incomplete system. In high-impact workflows, a well-designed escalation path can be part of the system's reliability model.

7. Build evaluation data from real work

A benchmark made entirely of synthetic examples can be useful for early development, but it is unlikely to capture the full messiness of production.

A stronger evaluation set combines several sources.

Representative tasks cover the routine work the agent is expected to perform.

Ambiguous tasks test whether the system asks for clarification or chooses a safe path.

Failure tasks simulate unavailable tools, malformed responses, timeouts and missing information.

Adversarial tasks test security boundaries and attempts to manipulate the agent.

Regression tasks preserve previously observed production failures so that the same mistake does not return after a model, prompt or tool change.

Real production traces are particularly valuable because they reveal where users actually create complexity. A workflow that appears simple in design documentation may contain dozens of variations once real requests arrive.

Every important failure should have a path back into the evaluation set.

8. Not every test needs a language model as the judge

Automated evaluation is attractive because agent runs can generate large amounts of data. But a language model should not automatically be used as the evaluator for every criterion.

Some checks are deterministic.

Was the correct account ID used? Was the transaction amount within the permitted threshold? Was an unauthorized endpoint called? Was the expected field present? Did the system create one record instead of two?

These conditions can often be tested with ordinary assertions.

Other criteria require semantic judgement. Did the response correctly summarize a complex case? Did it answer the user's actual question? Was the explanation sufficiently complete?

Those may benefit from rubric-based human review or model-assisted evaluation.

The strongest evaluation systems usually combine deterministic checks, specialized graders and human review rather than assuming one scoring mechanism can measure everything.

NIST's ARIA work provides a useful broader precedent here: its evaluation approach combines model testing, red teaming and user testing rather than relying on a single measurement method. citeturn0search8turn0search17

9. Use rubrics that describe observable behavior

A rubric should tell an evaluator what evidence constitutes success.

"The agent should reason well" is not a useful criterion.

"The agent must identify the latest approved policy, cite the source record and avoid making a decision when the policy version cannot be verified" is much easier to evaluate.

Good rubrics also separate partial success from critical failure.

An agent that retrieves the correct document but summarizes one minor detail incorrectly is different from an agent that retrieves the wrong policy and confidently recommends an action based on it.

The distinction matters because the remediation is different.

The first problem may require better extraction or summarization. The second may require changes to retrieval, source ranking, authorization or workflow design.

10. Test recovery, not just failure

Failures are inevitable in complex systems. The important question is what happens next.

Consider an agent that calls an inventory service and receives a timeout.

A poor recovery strategy is to repeat the same request indefinitely.

A better strategy might retry once, check whether the operation is idempotent, use an approved fallback source if one exists, and then escalate if the result remains unavailable.

The evaluation should measure this behavior.

Useful recovery metrics include:

  • time to detect failure
  • number of retries
  • successful recovery rate
  • duplicate-action rate
  • appropriate escalation rate
  • number of unnecessary tool calls after failure
  • percentage of tasks abandoned safely rather than completed incorrectly

A system that fails safely can be more useful than one that appears highly autonomous but continues acting after its assumptions have broken.

11. Measure cost and latency at the task level

Model cost alone does not tell the full story.

An agent can use an inexpensive model and still become expensive if it performs excessive retrieval, makes unnecessary tool calls or enters long retry loops. Conversely, a more capable model may be commercially sensible if it completes a complex workflow with fewer failures and less human intervention.

The relevant metric is often closer to cost per successful task than cost per model call.

The same principle applies to latency.

A ten-second response may be acceptable for a research workflow but unacceptable for a customer-facing checkout process. An internal analyst may tolerate a longer run if it produces a substantially better result. A real-time support workflow may need a strict response budget.

Evaluation should therefore define the service envelope before deployment.

That envelope might include maximum execution time, maximum tool calls, maximum retry count and maximum cost per completed task.

12. Repeatability matters more than a single impressive run

Agent behavior can vary from one execution to another. That means one successful run does not provide strong evidence of reliability.

A useful test should be repeated enough times to reveal variability, especially for critical workflows.

One way to think about this is to separate average success from consistency. An agent that succeeds on nine out of ten runs may look excellent in a demo. An agent that succeeds on every run of a smaller but business-critical task may be more appropriate for production.

This is also why evaluation datasets should be versioned.

When the model changes, the prompt changes, a retrieval index is rebuilt or a tool schema is modified, the same important cases should be rerun. A regression suite becomes the memory of the system's known failure modes.

13. Production monitoring completes the evaluation loop

Pre-release evaluation cannot predict every production failure.

Real users introduce unexpected language, incomplete information and workflows that were never represented in the original test set. External systems also change. APIs are updated. Documents become stale. Permissions change. New attack patterns appear.

Production monitoring therefore needs to feed the evaluation program.

A useful lifecycle looks like this:

  1. Define the task and acceptable behavior.
  2. Create representative and adversarial evaluation cases.
  3. Run deterministic and semantic checks.
  4. Red-team the workflow.
  5. Release with operational limits.
  6. Monitor production traces and incidents.
  7. Turn important failures into permanent regression tests.
  8. Re-evaluate after model, prompt, retrieval or tool changes.

This turns evaluation from a launch checklist into an ongoing engineering discipline.

14. A practical release scorecard

Before an agent enters production, an organization should be able to answer the following questions with evidence rather than confidence:

AreaRelease question
Task successDoes the agent complete representative tasks correctly?
GroundingDoes it use the correct and current evidence?
Tool useDoes it select and call tools correctly?
AuthorizationAre sensitive actions enforced outside the model?
SecurityDoes the system resist prompt injection and other agent-specific attacks?
RecoveryDoes it fail safely when tools or information are unavailable?
EscalationDoes it know when a human decision is required?
LatencyDoes execution fit the workflow's service requirements?
CostIs cost per successful task commercially acceptable?
ObservabilityCan operators reconstruct what happened after a failure?
RegressionAre known production failures permanently represented in testing?

A release decision should also specify which failures are unacceptable. This is especially important for systems that can change external state. A minor wording error and an unauthorized financial action should never be treated as equivalent failures simply because both reduce an aggregate score.

The difference between an impressive agent and a dependable one

The next stage of agent development will not be defined only by how many tasks systems can automate. It will also be defined by how convincingly organizations can demonstrate that those systems behave within known boundaries.

That requires a change in evaluation mindset.

The question is no longer simply whether an agent can perform a task.

It is whether the organization can explain:

  • what the agent is allowed to do
  • which tasks it performs reliably
  • where it tends to fail
  • how those failures are detected
  • what happens when a tool becomes unavailable
  • which actions require human approval
  • how the system handles untrusted information
  • how much a successful task costs
  • how production incidents become future tests

That is a much higher standard than a successful demonstration, but it is the standard required when an AI system moves from generating text to taking actions.

Agent evaluation is ultimately about establishing a defensible boundary of trust. Inside that boundary, automation can operate with measurable confidence. Outside it, the system should slow down, ask for clarification, request approval or hand the task to a person.

The strongest agent is therefore not the one that acts most autonomously.

It is the one whose autonomy is measurable, constrained and appropriate to the work it has been given.
