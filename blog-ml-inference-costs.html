Why the Real Machine Learning Problem Is Often Inference Cost, Not Model Size

by Dipankar Mukherji·AI / ML·~18 min read·target keyword: ML inference costs

Training gets the headlines. Inference gets the bill

There is something slightly backwards about how machine learning is discussed. Training is dramatic. Giant clusters, weeks of compute, a new benchmark, a huge model. Then the model ships and everybody discovers the real product has to answer millions of requests while meeting a latency target and staying inside a budget. Inference is where model architecture meets electricity, memory bandwidth, networking, batching, caching and user expectations. A model can be academically impressive and commercially awkward. That gap is where a lot of engineering work now lives.

Parameter count is a terrible proxy for product cost

A larger model may be slower and more expensive, but parameter count alone does not tell you what a request costs. Sequence length, context size, precision, accelerator type, batching strategy, concurrency and serving stack all matter. Two systems running models with similar parameter counts can have very different economics. Likewise, a small model can become expensive if an application sends enormous prompts or invokes it repeatedly for tasks a simpler rule could handle.

Memory is often the hidden constraint

For transformer inference, memory is not just model weights. There is also the working memory associated with the request, especially attention-related state and cached context. Longer prompts increase resource pressure. This is why context windows are not free. When a team says a model supports a very large context, the next question should be the next sentence to be about what that context costs in latency and memory under concurrent load. A feature can be technically available while still being economically impractical.

Quantisation is an engineering decision, not a magic compression button

Reducing numerical precision can cut memory use and improve throughput, but quality can shift depending on the model and workload. The practical question is not "can we quantise it". It is "where does quality actually move, and is the change acceptable for this task". Classification, extraction, summarisation and code generation can respond differently. Testing has to be workload-specific. A single benchmark is not enough when production queries are messy, multilingual, long and repetitive.

Batching changes the shape of the system

Batching can improve accelerator utilisation because hardware likes doing many similar operations at once. But user-facing applications care about response time. Aggressive batching can improve cost per token while hurting tail latency. The right configuration depends on traffic shape. A periodic reporting job can tolerate different delays from a customer support assistant. This sounds obvious, yet teams often tune the model first and the traffic pattern second.

Latency has a psychological side

A system that takes two seconds once is different from a system that takes two seconds for every interaction in a workflow. The perceived delay compounds when the product makes several model calls. This is one reason Measuring the whole request path rather than just model token speed. Retrieval, tool calls, reranking, policy checks and post-processing all sit between the user and the final answer. The fastest model in isolation can still produce the slowest product.

Caching can be more valuable than another model upgrade

If the application repeatedly asks similar questions, cacheable work is effectively free work after the first pass. Embedding caches, retrieval results, prompt fragments and deterministic transforms can reduce repeated computation. The challenge is correctness. A cached answer with stale context can be worse than a fresh expensive answer. So the interesting engineering problem becomes cache invalidation, scope and observability.

Routing is the underused idea

Not every task deserves the best model. A system can route easy requests to a small model, harder requests to a larger model and specific operations to deterministic code. This is not anti-LLM thinking. It is basic systems engineering. The model should match the task. Once costs are attached to requests, routing becomes a product decision rather than a purely technical optimisation.

The quality metric has to survive the cost metric

A cheaper inference stack is not an improvement if error rates rise and human review doubles. Evaluating quality and cost together. Cost per successful task is often more informative than cost per token. That shifts the conversation from "this model is 30% cheaper" to "we complete the task at lower total operating cost without changing the outcome users receive". That is the number a product manager can actually use.

Conclusion

Inference economics is where machine learning becomes an operating business rather than a benchmark. Model choice matters, but so do memory, context length, quantisation, routing, batching, caching, hardware and application design. The best system is rarely the one with the largest model. It is the one that produces the required quality at a latency and cost that the product can live with. That is a much more interesting engineering problem than parameter counting.
