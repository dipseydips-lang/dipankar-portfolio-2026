RAG Is Easy to Explain and Hard to Operate: The Enterprise Data Problem Nobody Shows in the Demo

by Dipankar Mukherji·Technology·~18 min read·target keyword: RAG enterprise AI

The demo is always a folder with six perfect PDFs

RAG looks almost inevitable in a presentation. Put documents in a folder, index them, ask a question and receive a grounded answer. Enterprise data is not a folder. It is SharePoint, email, PDFs, tickets, databases, permissions, duplicates, stale files and documents that contradict one another because different teams use different processes. The retrieval problem is therefore a data architecture problem before it is a language model problem.

One thing I keep noticing in this kind of work is that the first version of the explanation is usually cleaner than the real system. Real systems have exceptions. They have ownership questions, old documents, weird users, legacy integrations and the one edge case that appeared twice last month and now everybody is afraid of. That mess is not a reason to stop writing. It is the reason the writing becomes useful.

There is also a communication problem hiding inside the technical one. Engineers tend to describe components. Buyers describe outcomes. Operators describe interruptions. Compliance teams describe evidence. Good technical writing has to hold those views together without turning into a brochure. That means defining the thing, explaining the mechanism, then being honest about where the mechanism breaks.

A practical note: The more I read about the subject, the more I come back to a simple test: can a practitioner use this explanation to ask a better question? That is a better measure of technical content than how many fashionable terms appear in it. A useful article should leave the reader with a sharper mental model, not just a longer glossary.

Retrieval quality decides everything downstream

A language model cannot reliably answer from evidence it never received. That makes the retriever a critical component. The query needs to be represented in a way that finds the right information. The corpus needs sensible boundaries. Chunks have to preserve enough context. Ranking has to balance semantic similarity with exact terms and metadata. A poor retriever can produce a beautifully written wrong answer because the model is reasoning over the wrong evidence.

I would also resist the urge to turn every conclusion into a rule. Technology is full of trade-offs. A choice that is sensible for one workload can be wrong for another. A workflow that needs strict control may not need the same architecture as a low-risk internal tool. Context is not a disclaimer. Context is the actual answer.

Chunking is not a universal setting

Different documents have different structures. A policy manual wants sections and headings. A contract wants clauses. A troubleshooting article wants steps. A spreadsheet wants rows and columns. Cutting everything into identical token windows is easy to automate and easy to regret. Good RAG systems treat document structure as information instead of noise.

There is a temptation to sound certain when writing about a fast-moving category. I would rather mark the boundary between what the documentation says, what the evidence shows and what I think follows from it. That small distinction makes technical writing more credible because the reader can see which part is fact, which part is interpretation and which part still needs testing.

And then there is implementation. A lot of technology writing stops at the point where a reader would actually need to make a decision. I prefer going one step further. What has to change in the workflow. Who owns the result. What has to be monitored. What breaks first. What happens when the assumption is wrong. Those details are where a niche article earns its length.

Permissions are not optional metadata

An enterprise assistant should not retrieve a document simply because the embedding is similar. The user needs permission to see the source. This sounds basic but is one of the most important architectural constraints. Access control needs to survive the retrieval layer. Filtering after the model has already seen the content is too late. Security has to happen before generation.

Freshness changes the answer

A policy updated yesterday should beat a policy from three years ago. That means metadata, timestamps, versioning and source priority become useful retrieval signals. Enterprises often have multiple versions of the same document, and the newest is not always the correct one. Sometimes an older policy remains active while a new draft sits in a separate folder. RAG needs a concept of authority, not just similarity.

Citations improve trust but do not create correctness

Showing a source link next to an answer is helpful. It lets a reviewer inspect the evidence. But a citation can still point to a page that was misread or only partially supports the claim. The evaluation question is therefore whether the answer is faithful to the retrieved source, not merely whether a source was attached. This distinction matters for both users and governance teams.

Evaluation needs hard questions

Ask questions with known answers. Ask questions where the correct answer is "I do not know". Ask questions that require combining two documents. Ask questions where permissions matter. Ask about outdated information. Ask for a number buried in a long policy. Then measure retrieval recall, answer faithfulness and task success. A RAG system is not ready because twenty demonstration prompts worked.

Enterprise data creates contradictions

Two teams can legitimately document the same process differently because one describes the official policy and the other describes the local workaround. A model that merges those documents into one confident sentence can make the conflict invisible. Good retrieval and response design should surface contradictions instead of smoothing them away. Sometimes the most useful answer is: these sources disagree, here are the two versions.

Operations matter after launch

Documents change. Permissions change. Indexes need updates. Embedding models change. A source may disappear. Users ask new questions. RAG is therefore an evolving data product. Monitoring needs to include retrieval failures, empty results, access failures and source freshness, not just model latency.

My takeaway

RAG is powerful because enterprises already own a huge amount of useful information. It is difficult because that information is messy, permissioned, duplicated and constantly changing. The language model is only the last layer. Retrieval, document structure, metadata, security, freshness and evaluation determine whether the final answer is grounded or merely convincing. That is the story worth telling when the demo is over.
